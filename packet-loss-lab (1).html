Computer Networks · SDN + UDP · Packet loss detection and recovery

Lose a packet, find it, route around the fault.

A UDP application numbers every datagram, spots the holes in the sequence, asks for the missing ones again, and an SDN controller moves traffic to a second path when the first one degrades. This page explains each part, runs the whole loop live, and measures how fast it recovers compared with a static network.

02 · Mechanisms

What each part of the system does

Each card maps to one bullet of the project brief. The numbers are the values the lab and the reproduction code both use.

Task 1 · Sequence tracking

Every datagram carries a number

header = type (1 B) | seq (4 B, network order)
  • Sender increments seq per datagram, starting at 1.
  • Receiver keeps the highest seq seen and a set of seqs received.
  • cum = highest seq with no hole below it.
  • Duplicates are counted and discarded.
Task 2 · Missing packets

A gap is a hole below the highest seq

reorder wait 0.25 s · NACK repeat 1.8 s · max 16 per NACK
  • Any seq between cum+1 and highest that has not arrived is a gap.
  • A gap is only NACKed after 0.25 s, so reordered packets are not treated as lost.
  • A still-missing seq is NACKed again every 1.8 s.
Task 3 · ACK and retransmit

Cumulative ACK, selective ACK, NACK

ACK every 0.5 s · RTO 3.0 s × 1.4n, cap 8 s · max 5 retries
  • ACK carries cum plus up to 24 out-of-order seqs (SACK).
  • The sender frees everything the ACK covers.
  • A NACK triggers an immediate resend of the listed seqs.
  • Anything still unacked after the timer is resent; after 5 tries it is abandoned and counted as failed.
Task 4 · Path monitoring

Count both paths, probe both paths

poll 0.5 s · window 4 s (+1 s lag) · min 24 packets · threshold 20% · 4 bad polls
  • The controller injects one probe per path per poll (packet-out at s1, marked with the path's DSCP).
  • Data loss on the active path = packets counted leaving s1 (flow counters) minus packets arriving at h2 (receiver reports), over the last 4 s.
  • A path is healthy when at least 80% of its probes in the last 4 s arrived.
Task 5 · Dynamic rerouting

The controller rewrites the flow rules

FLOW_MOD prio 200 on s1 and s4 · failback after 6 s healthy
  • On link-down, PORT_STATUS triggers an immediate reroute, with no waiting for the loss estimate.
  • On degradation, the controller moves to the alternate path only if its probes are healthy.
  • When the primary recovers, traffic returns to it after 6 s of clean probes.
  • Static baseline: the same faults with rerouting disabled.
Task 6 · Recovery and measurement

Time-stamped recovery and loss windows

loss windows: before fault · during 15 s · after 15 s
  • The recovery clock starts when the fault is injected.
  • Loss is compared in three windows, and goodput is measured per second.
  • Every run uses three fixed seeds, so the numbers can be reproduced.

04 · Recovery time

How recovery time is measured

One clock per incident, started at fault injection. Each milestone is recorded when it happens, not estimated afterwards.

Milestones

  1. Detect · the controller decides the path is bad, from PORT_STATUS or from four bad polls (2 s).
  2. Reroute · both FLOW_MODs are applied on s1 and s4, so new packets follow the other path.
  3. First packet · the first data packet is delivered over the new path.
  4. Cleared · every packet up to the highest seq has been delivered (retransmits included).

05 · Reproduce

Mininet topology, controller and socket code

The lab above runs the same protocol and controller rules in the browser. The files below are the Mininet implementation in the project repository. They were run end to end here, on Mininet with Open vSwitch and OS-Ken, for the link-failure and meter-emulated loss faults; the netem loss fault needs the sch_netem kernel module, which this test machine did not have. Measured runs are in the repository's results folder.

  1. 1 · Start the controller

    Run sudo python3 run_controller.py. It loads pathguard.py on TCP 6633 and installs base forwarding when the four switches connect. Set PATHGUARD_STATIC=1 for the static baseline.

  2. 2 · Run one experiment

    Run sudo python3 run_experiment.py --out results/demo --fault loss --loss 60. It builds topo.py, checks the port map, starts receiver.py on h2 and sender.py on h1, injects the fault and saves the logs. Faults: none, loss (netem), meter, down.

  3. 3 · Analyse

    Run python3 analyze.py results/demo. It writes metrics.json: loss before, during and after the fault, detection, reroute, first packet on the alternate path, backlog cleared, and goodput.

  4. 4 · Repeat for every scenario

    Run sudo ./run_validation.sh. It runs each fault in SDN and static mode with repeats, then prints the summary table from summarize.py.

Common Questions

    

      
Why use sequence numbers and a cumulative ACK, not a per-packet ACK?
One cumulative number says every packet up to it arrived, which is cheap to send and robust to lost ACKs, since the next ACK repeats the information. The SACK list adds the out-of-order packets, so the sender only resends real holes.

      
Why wait 0.25 s before sending a NACK?
UDP can reorder packets, especially across paths with different delays. Without the wait, every reordered packet would trigger a needless retransmission. The wait trades a little recovery latency for fewer duplicates. The duplicate count in the results shows the cost.

      
Why does the controller use two signals for loss?
Probes measure path health even when no data is flowing. The data-loss estimate measures what the application actually experiences. Requiring four bad polls in a row stops one unlucky sample from triggering a reroute, and an application report can confirm the problem.

      
What happens if both paths fail?
The controller finds no healthy alternate and stays on the current path, logging "no healthy alternate path". The sender keeps retransmitting until the 5-retry limit, then abandons packets and counts them as failed. The residual loss figure in the comparison shows this case.

      
Why is the static baseline needed?
Without it, the improvement cannot be attributed to rerouting. The static run uses the same seeds, faults and protocol, with only the controller's reroute logic disabled. The difference is what the SDN loop buys.

      
Why is failback delayed by 6 s?
A link that has just recovered can flap. Waiting for several seconds of clean probes avoids moving traffic back and forth. The cost is slightly longer time on the alternate path.
